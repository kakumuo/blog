# Background
Just some background on this. I enjoy playing videogames from time to time, and, after coming off work, I'll lean towards with low investment. Typically, these will be perma-death or indie games. One such game is [Risk of Rain 2](https://en.wikipedia.org/wiki/Risk_of_Rain_2). Its a roguelike where you survive waves of enemies in differnt environmetns collecting items along the way in hopes of escaping the planet. Additionally, it's a game that I have been playing since high school with the first installation. And with around 1,000 hours put into it, I would not only call it my favorite rougelike, but also a game that I find fairly stale. I wanted to find a way to add some difficulty to the game without really having to add new game or character models. So the easiest route for somehting like that would be with UI implementations using existing game assets. 

# Brainstorming
I settled on creating an inventory management system akin to [Resident Evil 2's Inventory System]{https://raw.githubusercontent.com/kakumuo/blog/refs/heads/main/posts/r2-mod-active-inventory/re_inventory_system.webp}. The idea is that you would need to constantly have to stop and rearrange the items that you pick up as to make room for additional items. One of the issues that I noticed with getting far in a run was that there would be a point where, there was no reason to not pick up an item. With this mod, however, there would be an added difficulty of having to be aware of the items that you pick up. 

Originally, this was inteded to be a dedicated game mode with modifiers around this mechanic. But seeing as this was my first mod, I felt that it would be more suitable to work on something with a smaller scope (that was definitley the right play). Even with the shortened scope, I still had to stash some implementations just because I felt that I was working on this for a bit longer than I anticipate, that being: 
1. __Inventory Buffs__: Depending on how items are oriented and placed adjacent to other items, the player would get different buffs
2. __Drones__: When recruiting drones, a replica of the drone would be added to the inventory. The player would then be able to attach items to the drone depending on its adjacency to other items. 

# Implementation
It's been some time since I did work in Unity. I believe the last project that I worked on in that engine was a game that I made for school where I created pong, but with bots I trained using Unity's ML agents library. 

Getting things up and running didn't take too long. The best course of action is to do the development in a separate Unity Project, the port the code into a separate folder for the game plugin. This allows for the mod to be uploaded to the public reposotiry witout Unity's boilerplate. Since most of the implementation was UI, I figured that I could take a literal approach to the MVC pattern. Where the `Model`, would be different classes that could be seen as the 'Backend' and the `View` & `Controller` (`View-troller`) would be the in-game UI assets.  

> "How might the design change if I needed to implement the same features for a CLI application?"

What do I mean by this? Lets say that you wanted to develop an app that gives users the ability to open one or more files. You might offer them the ability Drag and Drop, to Copy and Paste or to Select a file through a File Chooser window. In the same way, what options do you have when it comes to building this out through a CLI app? There's really only one, the file path as text. In order to accomidate both, you wouldn't create one method for each possible action, but just one method and adjust it on the front-end or CLI side. 

This is the mindset that I kept when designing the `Model` components, thus ensuring they are treated like an API. With the codebase framed this way, I can call the `Model` components freely and not tightly couple them with the `View-troller`. I can also fully develop either layer with proper testing. 

Given this would be designed like an API, I had one entrypoint for the entire `Model` under `InventoryModel`. This contains all `AddItem` and `RemoveItem` methods. Anywhere I needed the `InventoryModel` to interact with the GameEngine or Risk of Rain 2 Mod Libraries would be done through a `Service` class, that being the `ItemService`. Designing things like this gave me some wiggleroom for portability when it came time to move things outside of Unity project and into the actualy mod plugin folder. 

I took a similar approach for the `View-troller` where the single entrypoint was through the `InventoryUI` class that makes use of the `UIAssetService` class for interfacing with additional game files. Each UI element would have its own `Controller` and would be updated from the core `InventoryUI` class. Additionally, actions driven by the child controllers would interface back with the `InventoryUI` class which would in turn either interact with the `InventoryModel` or with the game itself. 

One issue, however, is that it is not possible to port over game assets directly into the mod plugin, even through an asset bundle. The recommended approach is to rebuild any UI via code at runtime. This ended up being where the majority of developent time was spent, since the way that the game components are rendered in the Unity editor and they way that they are rendered in game are ever-so-slightly different. Alignment, positioning, margins, tree heirarchy are all things that had to be adjusted and tested over and over. Furthermore, since I was never able to get hot realoading up and running, each change needed a separate restart of the game. One unintentional benefit of this, though, is that I feel that I improved my working memory, by having to keep track of both working code changes and additional revisions after running the game. 

Another issue is that there is little to no documentation when it comes to how the game library actually works. There is a wiki, but it mostly references the different things you would need to be aware of when developing a mod. The best resource for what the game libraries actually the Discord, which is limited to Discord's search capability and whether or not someone decided to [paste their code as a picture]{https://raw.githubusercontent.com/kakumuo/blog/refs/heads/main/posts/r2-mod-active-inventory/picard-facepalm.jpg}.

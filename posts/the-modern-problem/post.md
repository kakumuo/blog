# Background
As a part of trying to expand my horizons when it comes to software development, I decided to pick up some of the more modern languages. From various job applications, videos, and forums, I constantly encounter people mentioning that they are working with "Go". I've also been watching more tech-aligned YouTubers, many of which are always mentioning how Rust is going to be the next big thing. After some time of constantly being bombarded with promotions from both sides, I felt that it was time to see if they really lived up to the hype. 

## Go vs Rust
The first thing that I experienced was how different the learning curve is for both languages. I first started with Go, where after a few days of following some basic instruction and the interactive tutorial, I could say that I got a good grasp on how to write effective code. As with Rust, its been about a month now, and I still don't feel like I've gotten a good grasp of the unique aspects of the language. I'm usually faced with the point where I finish writing a few code blocks and I'm constantly rerunning to ensure that lifetimes and references are valid. 

On a more personal note, I would say that I didn't really *"feel"* anything from learning Go, but my passion for writing code was reignited when learning Rust. There is something about adding a new rule to the language that makes it feel more of a game than a means to an end. And in this case those rules help to improve performance substantially.

Additionally, I appreciate the little nuances and features that both of these languages offer. Rust's use of expressions like `match` and `if` make consolidating code much neater than something you would find in other languages. The way that Rust uses `enums` is something that I would like to see elsewhere. Whereas with Go, `defer` is an immediate game changer in handling function returns. And the way that Go limits you to using composition through interfaces alleviates many of the headaches associated with inheritance. Furthermore, both languages sport excellent tools for managing dependencies and the ability to compile your code into a single executable.  


## The Modern Problem
It seems like both languages are trying to solve long-standing problems in a modern way. Rust is trying to tackle undefined behavior resulting from mismanaged memory and Go is handling complex and obfuscated codebases. I can see how Rust is popular among enthusiast communities, but I don't expect it to be something that is popular among tech companies. It doesn't feel that it would scale well, and can only introduce headaches as developers have to work their way around borrow checking rules. In that regard, I can see Go excelling with large teams, where everyone is limited to writing similar code in the same, readable and maintainable way. But do to how limiting Go is syntactically, it can make it difficult to write something that would normally be straight forward in a non-roundabout way. 

I'm not sure if I would recommend either of these languages to someone starting off for the first time. In Rust's case, you should have a good grasp on non-GC languages and the potential problems that can arise from poor memory management. I wouldn't even recommend a beginner to work with a non-GC language at all; there's just simply too many moving parts. In Go's case, although it is pretty easy to pick up, you don't get the full grasp of why certain things are restricted unless you come from somewhere else with more freedom. There's quite a few rules surrounding the ideologies behind the language that can be found [here](https://commandcenter.blogspot.com/2012/06/less-is-exponentially-more.html). That being said, and ignoring all biases, I would probably recommend a beginner to work, first with something that is closely related to their field of interest, but next with a strongly typed, object oriented language. Strong typing would add some needed friction to ensure that code is being written in a more sensible and clean manner. Additionally, OOP languages allow for a representation of concepts in more tangible form. And given its popularity in previous years, Java works best to fit both of these criteria.
